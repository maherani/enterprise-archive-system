# مأموریت: مستندسازی جامع و ماژولار تاریخچه نیازمندی‌ها، معماری و پیاده‌سازی پروژه Enterprise Archive System

تو در طول توسعه پروژه **Enterprise Archive System** مجموعه‌ای از نیازمندی‌ها را از من دریافت کرده‌ای. برای هر نیازمندی، ابتدا تحلیل و طراحی ارائه شده، سپس پس از تأیید من، پیاده‌سازی، تست، اصلاح نهایی و در نهایت Commit/Push انجام شده است.

اکنون مأموریت تو این است که **تاریخچه نهایی و واقعی این نیازمندی‌ها و معماری حاصل از آن‌ها را به‌صورت مستندات ماژولار، دقیق و قابل نگهداری در خود Repository ثبت کنی.**

هدف این مستندات این است که در آینده بتوان هر بخش از سیستم را مستقل از تاریخچه گفتگوها مطالعه کرد و دقیقاً فهمید:

* این نیازمندی چه بوده است؟
* هدف آن چه بوده؟
* چه معماری برای آن تأیید شده است؟
* چه اجزایی برای اجرای آن ایجاد یا تغییر کرده‌اند؟
* منطق عملکرد آن چیست؟
* چه Roleها، Permissionها، Tagها، APIها، سرویس‌ها و Database Changeهایی درگیر هستند؟
* وضعیت نهایی و قابل اتکای آن در Repository چیست؟

قبل از شروع مستندسازی، ابتدا وضعیت فعلی پروژه را به‌طور کامل بررسی کن.

در صورتی که بین تاریخچه توسعه و وضعیت فعلی Repository تفاوتی وجود داشت، **مستندات باید وضعیت نهایی و موفق فعلی سیستم را مبنا قرار دهند.**

# 1. ساختار فایل‌ها

یک دایرکتوری اختصاصی ایجاد کن:

```text
docs/requirements/
```

تمام مستندات Requirementها باید فقط در این مسیر قرار بگیرند.

برای هر Requirement دقیقاً یک فایل Markdown مستقل ایجاد کن.

فرمت نام فایل:

```text
01_<short_english_name>.md
02_<short_english_name>.md
03_<short_english_name>.md
...
```

نام فایل‌ها باید:

* انگلیسی باشد.
* کوتاه باشد.
* معنی‌دار باشد.
* بر اساس ترتیب تاریخی/اجرایی Requirementها شماره‌گذاری شود.
* شماره‌ها پیوسته باشند.
* یک Requirement در چند فایل پراکنده نشود، مگر برای یک دلیل بسیار مشخص و ضروری.

نمونه:

```text
01_base_infrastructure.md
02_admin_folder_governance.md
03_dynamic_auto_tagging.md
04_backup_restore.md
```

**شماره‌گذاری را بر اساس تاریخچه واقعی پروژه انجام بده و از ساختن Requirement فرضی خودداری کن.**

# 4. ثبت «نیازمندی واقعی» و «طرح تأییدشده»

برای هر Requirement، تا حد امکان دو بخش مستقل داشته باش:

## 4.1 شرح نیازمندی

در این بخش **نیازمندی واقعی درخواست‌شده توسط من** را مستند کن.

این بخش باید نشان دهد:

* مسئله چه بوده؟
* چه رفتاری مورد انتظار بوده؟
* چه محدودیت‌هایی تعیین شده؟
* چه قوانین سازمانی وجود داشته؟
* چه شرایطی باید رعایت می‌شده؟
* چه چیزی صراحتاً نباید اتفاق می‌افتاده؟

## 4.2 معماری و طرح اجرایی تأییدشده

در این بخش، **طرح نهایی تأییدشده‌ای که مبنای پیاده‌سازی قرار گرفته** را مستند کن.

این بخش باید شامل مواردی مانند:

* Architecture
* Components
* Data Flow
* Workflow
* API Design
* Database Design
* Permission Model
* Security Model
* Integration Points
* Validation
* Error Handling
* Test Strategy

باشد.

### نکته مهم

هدف بازسازی گفتگوی چت به‌صورت تحت‌اللفظی نیست.

منظور از «متن کامل طرح تأییدشده» این است که **تمام محتوای فنی و تصمیم‌های معماری تأییدشده** حفظ شوند و هیچ جزئیات مهمی حذف نشود.

# 5. فقط وضعیت نهایی موفق مستند شود

در مستندات Requirementها:

* باگ‌های تاریخی را مستند نکن.
* تلاش‌های ناموفق را مستند نکن.
* Debug sessionها را مستند نکن.
* راه‌حل‌های ردشده را مستند نکن.
* نسخه‌های موقت و آزمایشی را مستند نکن.
* خطاهایی که در مسیر توسعه رخ داده و دیگر بخشی از سیستم نهایی نیستند را وارد مستندات نکن.

مستند باید روایت **نسخه نهایی و موفق Feature** باشد.

با این حال، اگر یک محدودیت، تصمیم طراحی، یا رفتار خاص واقعاً در نسخه نهایی سیستم وجود دارد، باید آن را مستند کنی حتی اگر ناشی از یک تصمیم اصلاحی در طول توسعه بوده باشد.

# 6. اتصال Requirement به کد واقعی

برای هر Requirement، تا حد امکان باید مشخص شود که این قابلیت در کدام بخش‌های Repository پیاده‌سازی شده است.

برای مثال:

```text
Backend:
- path/to/file.py
- path/to/service.py

Frontend:
- path/to/page.tsx
- path/to/component.tsx

Database:
- migration_name
- table_name

Tests:
- tests/test_x.py
```

این ارجاع‌ها باید بر اساس **فایل‌های واقعاً موجود در Repository** باشند.

هیچ فایل، Class، API یا ساختاری را که در Repository وجود ندارد به‌صورت فرضی مستند نکن.

# 7. قالب پیشنهادی هر Requirement

در صورت مناسب بودن برای آن Requirement، ساختار فایل به شکل زیر باشد:

```markdown
# عنوان نیازمندی

## 3. Scope

## 4. Actors و Roleها

## 5. قوانین و محدودیت‌ها

## 8. Workflow

## 9. Backend

## 10. Frontend

## 11. Database

## 12. APIها

## 13. Permission و Security

## 14. Audit و Logging

## 15. Notification

## 16. ساختار فایل‌ها و اجزای پیاده‌سازی
```

این ساختار **الزامیِ خشک نیست**؛ اگر Requirement خاصی بعضی بخش‌ها را ندارد، بخش غیرضروری را ایجاد نکن.

در مقابل، اگر Requirement پیچیده‌تر است، بخش‌های بیشتری اضافه کن.

# 8. ارتباط بین Requirementها

بعضی قابلیت‌های پروژه به یکدیگر وابسته هستند.

در چنین مواردی، در انتهای مستند مشخص کن:

* این Requirement به کدام Requirementهای قبلی وابسته است.
* کدام قابلیت‌های بعدی به آن وابسته هستند.
* چه ارتباطی بین آن‌ها وجود دارد.

مثلاً:

```text
وابستگی:
02_admin_folder_governance
03_dynamic_auto_tagging

این Requirement از Permission Model معرفی‌شده در Requirement 02 استفاده می‌کند.
```

# 9. دقت در شماره‌گذاری Requirementها

قبل از ایجاد فایل‌های شماره‌دار، ابتدا تاریخچه پروژه را بررسی کن و مشخص کن:

* چند Requirement واقعی تاکنون اجرا شده است.
* ترتیب منطقی/تاریخی آن‌ها چیست.
* نام مناسب هرکدام چیست.

**از حدس زدن Requirementها خودداری کن.**

اگر یک Commit صرفاً تغییر داخلی، Refactor، Fix یا Documentation بوده و یک Requirement مستقل محسوب نمی‌شود، برای آن یک Requirement جدید نساز.

هدف مستندسازی **Feature / Requirementهای واقعی** است، نه تمام Commitها.

# 10. استراتژی تولید مرحله‌ای

به دلیل تعداد زیاد Requirementها، تولید مستندات باید مرحله‌ای انجام شود.

## مرحله اول

در همین مرحله فقط:

```text
docs/requirements/
```

را ایجاد کن و فقط سه فایل اول را تولید کن:

```text
01_*.md
02_*.md
03_*.md
```

بعد از ایجاد این سه فایل:

* محتوای آن‌ها را بررسی کن.
* اطمینان حاصل کن با وضعیت واقعی Repository منطبق هستند.
* هیچ Requirement دیگری را در همین مرحله تولید نکن.
* Commit و Push نهایی کل مستندات را نیز در این مرحله انجام نده.

سپس متوقف شو و منتظر تأیید من بمان.

---

## مرحله دوم

پس از تأیید من:

```text
04_*.md
05_*.md
06_*.md
```

را ایجاد کن.

سپس متوقف شو.

---

این الگو را ادامه بده:

```text
07 - 09
10 - 12
13 - 15
...
```

تا زمانی که تمام Requirementهای واقعی پروژه مستند شوند.

# 11. Commit و Push

تا زمانی که **تمام Requirementها** مستند نشده‌اند، Commit نهایی و Push نهایی انجام نده.

پس از تکمیل کامل مستندات:

1. همه فایل‌ها را بررسی کن.
2. نام‌گذاری و شماره‌گذاری را بررسی کن.
3. صحت لینک‌ها و مسیر فایل‌ها را بررسی کن.
4. تطابق مستندات با Repository را بررسی کن.
5. از ایجاد فایل‌های تکراری یا جاافتاده جلوگیری کن.
6. سپس یک Commit مناسب برای مستندات ایجاد کن.
7. در نهایت Push انجام بده.

پیام Commit باید واضح و مرتبط با Documentation باشد، برای مثال:

```text
docs: add modular requirements documentation
```

---

# 12. قانون دائمی Living Documentation

این بخش از این لحظه یک **قانون دائمی پروژه** است.

هر زمان در آینده یک Requirement جدید از من دریافت شد و فرآیند زیر کامل شد:

```text
Requirement
→ Design
→ Approval
→ Implementation
→ Test
→ Final Approval
```

باید در پایان همان Feature، یک مستند جدید در:

```text
docs/requirements/
```

ایجاد شود.

شماره Requirement جدید باید ادامه آخرین شماره موجود باشد.

مثلاً اگر آخرین فایل:

```text
12_advanced_search.md
```

باشد، Requirement بعدی باید مانند:

```text
13_new_feature.md
```

ثبت شود.

این مستند جدید باید شامل همان استانداردهای این مأموریت باشد و باید همراه با تغییرات Feature در Git ثبت شود.

---

# 13. قانون مهم برای آینده

بعد از فعال شدن این قانون:

**هیچ Requirement جدیدی نباید بدون مستند مربوط به خودش وارد وضعیت نهایی پروژه شود.**

در پایان هر Feature جدید:

1. پیاده‌سازی انجام شود.
2. تست شود.
3. وضعیت نهایی تأیید شود.
4. مستند Requirement ایجاد/به‌روزرسانی شود.
5. سپس Commit/Push انجام شود.

در صورت اصلاح اساسی یک Requirement موجود، مستند همان Requirement نیز باید متناسب با وضعیت جدید به‌روزرسانی شود.

# 14. معیار پذیرش این مأموریت

این مأموریت زمانی موفق محسوب می‌شود که:

* پوشه `docs/requirements/` وجود داشته باشد.
* هر Requirement واقعی یک فایل مستقل داشته باشد.
* شماره‌گذاری فایل‌ها پیوسته و صحیح باشد.
* نام فایل‌ها انگلیسی و محتوای آن‌ها فارسی باشد.
* مستندات با وضعیت واقعی Repository منطبق باشند.
* جزئیات مهم معماری حذف نشده باشند.
* اطلاعات ساختگی وارد مستندات نشده باشد.
* فقط وضعیت نهایی سیستم مستند شده باشد.
* وابستگی بین Requirementها مشخص باشد.
* در آینده بتوان مستندات را به‌عنوان **Living Documentation** ادامه داد.
