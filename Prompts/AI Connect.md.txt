حتماً. برای این نیازمندی بهتر است پرامپت فقط روی «اتصال به Ollama» تمرکز نکند؛ چون هدف تو در واقع ایجاد یک **لایه هوش مصنوعی سازمانی روی مستندات آرشیو** است که هم تحلیل کند و هم در آینده بتواند عملیات مجاز انجام دهد.

این نسخه را طوری نوشته‌ام که Antigravity ابتدا معماری فعلی پروژه و قابلیت‌های AnythingLLM/Ollama را بررسی کند و **بدون تغییر کد، طرح پیشنهادی بدهد**.

می‌خواهم یک قابلیت جدید و مهم به پروژه آرشیو و مستندات سازمانی اضافه شود.

## هدف اصلی

می‌خواهم سیستم آرشیو و مستندات سازمانی به یک **دستیار هوش مصنوعی Local/On-Premise** که داخل سازمان اجرا می‌شود متصل شود.

هدف این است که هوش مصنوعی بتواند با رعایت کامل Permissionها و سیاست‌های امنیتی سازمان، مستندات موجود در سامانه آرشیو را برای مواردی مانند:

* جستجو
* تحلیل
* خلاصه‌سازی
* پاسخ به سؤالات
* استخراج اطلاعات
* مقایسه اسناد
* دسته‌بندی
* پیدا کردن ارتباط بین اسناد
* تهیه گزارش
* شناسایی الگوها
* تحلیل محتوای مستندات
* و سایر قابلیت‌هایی که یک LLM می‌تواند روی اسناد انجام دهد

استفاده کند.

این هوش مصنوعی باید کاملاً **Local و On-Premise** باشد و اسناد محرمانه سازمان نباید برای پردازش به سرویس‌های Cloud یا APIهای عمومی ارسال شوند.

# 1. محیط هوش مصنوعی سازمان

فرض اولیه این است که در سازمان یک سامانه AI محلی وجود دارد که می‌تواند شامل موارد زیر باشد:

* Ollama
* AnythingLLM
* یک یا چند مدل زبانی Local
* Vector Database
* Embedding Model
* RAG Pipeline

اما معماری نباید به شکل Hard-coded فقط به Ollama یا AnythingLLM وابسته شود.

ابتدا بررسی کن که بهترین روش Integration با معماری فعلی چیست.

اگر AnythingLLM قابلیت API مناسب برای این کار دارد، آن را بررسی کن.

اگر Ollama مستقیماً برای برخی عملیات مناسب‌تر است، آن گزینه نیز بررسی شود.

هدف نهایی باید ایجاد یک **AI Integration Layer** بین سیستم آرشیو و دستیار هوش مصنوعی باشد.

# 3. مهم‌ترین اصل امنیتی — Permission-Aware AI

این بخش بسیار مهم است.

هوش مصنوعی نباید بتواند تمام مستندات سازمان را مشاهده کند.

اگر کاربر فقط به گروه یا پوشه خاصی دسترسی دارد، AI نیز باید دقیقاً همان محدوده دسترسی را رعایت کند.

برای مثال:

```text
User A
  │
  ├── Group: SOC
  │
  ├── Folder A ✓
  ├── Folder B ✓
  └── Folder C ✗
```

AI برای User A نباید بتواند محتوای Folder C را در پاسخ‌های خود استفاده کند.

حتی اگر سند Folder C قبلاً وارد Vector Database شده باشد، نباید در Retrieval برای User A قابل استفاده باشد.

بنابراین Permission باید **قبل از Retrieval و در زمان Query** نیز بررسی شود.

---

# 4. جلوگیری از نشت اطلاعات از طریق AI

سیستم باید در برابر این سناریوها مقاوم باشد:

* کاربر درخواست اطلاعاتی از گروه دیگر کند.
* کاربر بخواهد AI Permissionها را دور بزند.
* کاربر از Prompt Injection داخل یک سند استفاده کند.
* یک سند حاوی دستوراتی باشد که AI را وادار به افشای اطلاعات کند.
* کاربر از AI بخواهد اسناد محرمانه گروه دیگری را خلاصه کند.
* کاربر از طریق سؤال غیرمستقیم اطلاعات محرمانه را استخراج کند.

AI نباید صرفاً به Prompt برای حفظ امنیت متکی باشد.

Permission Enforcement باید در **Application Layer / Retrieval Layer** انجام شود.

# 5. اتصال اسناد به AI

باید مشخص شود که اسناد چگونه از Archive به AI منتقل یا در اختیار AI قرار می‌گیرند.

بررسی کن که آیا بهتر است:

### روش A

AnythingLLM مستقیماً از Storage اسناد استفاده کند.

### روش B

سیستم Archive اسناد مجاز را از طریق API در اختیار AI قرار دهد.

### روش C

یک Index/Vector Pipeline جداگانه ایجاد شود.

### روش D

روش دیگری که با معماری فعلی پروژه سازگارتر است.

مزایا و معایب هر روش را بررسی کن و یک روش اصلی پیشنهاد بده.

---

# 6. Indexing و Synchronization

سیستم باید بتواند تغییرات اسناد را به AI منتقل کند.

برای مثال:

```text
Upload
   ↓
New Document
   ↓
Extract Text
   ↓
Chunk
   ↓
Embedding
   ↓
Vector Index
```

همچنین:

```text
Document Updated
        ↓
Re-index
```

و:

```text
Document Deleted
        ↓
Remove From AI Index
```

و:

```text
Document Renamed
        ↓
Update Metadata
```

نیز باید در نظر گرفته شود.

اگر یک سند Permission آن تغییر کرد، دسترسی AI به آن نیز باید مطابق Permission جدید تغییر کند.

# 7. Metadata و Tagها

AI باید علاوه بر متن سند، در صورت امکان Metadata آن را نیز بشناسد.

مانند:

* نام فایل
* مسیر
* پوشه والد
* گروه
* مالک
* کاربر ایجادکننده
* تاریخ ایجاد
* تاریخ تغییر
* نوع فایل
* Tagها
* Permissionها
* وضعیت سند

این Metadata می‌تواند برای Filtering و Retrieval استفاده شود.

برای مثال:

> «تمام اسناد مربوط به Incidentهای گروه SOC در سال گذشته را پیدا کن.»

AI باید بتواند ابتدا با Metadata Filtering انجام دهد و سپس RAG را روی اسناد مجاز اجرا کند.

# 8. قابلیت‌های مورد انتظار AI

معماری باید امکان استفاده از AI برای قابلیت‌های زیر را فراهم کند:

### جستجوی هوشمند

کاربر بتواند به زبان طبیعی سؤال کند:

> «اسناد مربوط به Incidentهای شبکه در ماه گذشته را پیدا کن.»

### پرسش و پاسخ

> «در این مستندات چه سیاستی برای Incident Response تعریف شده؟»

### خلاصه‌سازی

> «این سند را خلاصه کن.»

### مقایسه

> «تفاوت نسخه جدید و قبلی این دستورالعمل چیست؟»

### استخراج اطلاعات

> «تمام سرورهای ذکرشده در این مستندات را استخراج کن.»

### تحلیل

> «چه مشکلات تکرارشونده‌ای در گزارش‌های Incident دیده می‌شود؟»

### گزارش‌سازی

> «یک گزارش مدیریتی از وضعیت Incidentهای ثبت‌شده تهیه کن.»

### ارتباط بین اسناد

> «کدام مستندات به این دستورالعمل مرتبط هستند؟»

### طبقه‌بندی

در صورت مناسب بودن معماری:

> «این اسناد را بر اساس موضوع دسته‌بندی کن.»

# 9. قابلیت‌های عملیاتی AI

در آینده ممکن است بخواهیم AI فقط اطلاعات را تحلیل نکند و بتواند **عملیات مجاز** نیز انجام دهد.

برای مثال:

* ایجاد درخواست
* ایجاد Folder
* جستجوی کاربران
* مشاهده وضعیت درخواست
* ایجاد گزارش
* پیشنهاد Tag
* پیشنهاد Permission
* بررسی اسناد
* ایجاد Task
* تهیه گزارش دوره‌ای
* پایش وضعیت سیستم

اما این بخش باید با مفهوم **Tool Calling / Function Calling** طراحی شود.

AI نباید مستقیماً به Database یا File System دسترسی داشته باشد.

به جای آن:

```text
AI
 ↓
Tool/API
 ↓
Authorization
 ↓
Operation
```

انجام شود.

# 12. نمایش Source / Citation

در پاسخ‌های مبتنی بر اسناد، بهتر است مشخص شود:

* پاسخ از کدام سند گرفته شده.
* نام فایل چیست.
* مسیر فایل چیست.
* در صورت امکان صفحه یا بخش مربوطه چیست.

مثلاً:

...

این قابلیت برای استفاده سازمانی بسیار مهم است.

یک نکته مهم هم در این نیازمندی گذاشتم که به نظرم برای پروژه سازمانی تو **خیلی حیاتی** است: AI نباید صرفاً «به یک Workspace در AnythingLLM» دسترسی داشته باشد و تمام. **Permissionهای خود آرشیو باید مرجع نهایی دسترسی AI باشند.** این باعث می‌شود اگر مثلاً یک کاربر از گروه SOC باشد، AI نتواند با یک سؤال هوشمندانه اطلاعات گروه CERT را از Vector DB بیرون بکشد.
