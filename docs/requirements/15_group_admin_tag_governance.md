# نیازمندی ۱۵: مدیریت تگ‌های اختصاصی گروه توسط ادمین گروه و ایزولاسیون کامل بین‌گروهی (Group-Specific Tag Management by Group Admin & Cross-Group Isolation)

## ۱. بیان مسئله و اهداف (Problem Statement & Business Objectives)
در سامانه بایگانی اسناد سازمانی (**Enterprise Archive System**)، اسناد محرمانه در ساختار سلسله‌مراتبی پوشه‌های گروهی (نظیر `SOC`, `CERT`, `IncidentMNG`, `NetWork`, `Office`) نگهداری می‌شوند. با توجه به حجم فزاینده اسناد سازمانی و نیاز به دسته‌بندی‌های تخصصی درون‌بخشی، قابلیت جدیدی به سیستم اضافه گردید که اهداف زیر را محقق می‌سازد:

1. **انعطاف در دسته‌بندی داخلی گروه:** ادمین هر گروه سازمانی (Group Admin / Subadmin) بتواند بدون نیاز به مداخله ادمین کل سیستم، تگ‌های اختصاصی متناسب با فرایندهای بخش خود (نظیر «محرمانه_سطح۱»، «گزارش_فوری_پدافند»، «مستندات_بازرسی_۱۴۰۵») را ایجاد، حذف و به اسناد متصل نماید.
2. **عدم اختلال در سیستم تگ‌گذاری خودکار (Auto-Tagging Preservation):** بارگذاری اسناد توسط کاربران عادی همواره تگ‌های سلسله‌مراتبی پوشه‌های والد را به‌صورت خودکار دریافت کرده و رفتار پیشین سامانه بدون هیچ‌گونه رگرسیون حفظ می‌گردد.
3. **حاکمیت امنیتی مطلق و منع هرگونه نشت بین‌گروهی (Strict Cross-Group Isolation):** ادمین یا اعضای یک گروه به هیچ‌عنوان نباید بتوانند تگ‌های گروه دیگر را مشاهده کرده، ایجاد نمایند یا به فایل‌های گروه دیگر الصاق کنند.
4. **کنترل سطح دسترسی بدون دور زدن (Zero-Bypass Authorization):** حتی کاربر مدیر ارشد (`admin`) بدون عضویت صریح در نقش Subadmin آن گروه، مجاز به ایجاد، حذف یا اعمال تگ‌های اختصاصی آن گروه نمی‌باشد.
5. **ماندگاری و حفاظت در برابر هرس خودکار (Reconciliation Protection):** تگ‌های ایجادشده توسط ادمین گروه هرگز در اثر بازآرایی پوشه‌ها، جابجایی اسناد یا اجرای دستورات هرس دوره‌ای هرس (Prune) نمی‌شوند.

## ۲. اصل حاکم و مدل امنیتی Zero-Bypass
بر اساس اصول حاکمیتی سامانه، معماری اعتبارسنجی در تمامی سطوح هفت‌گانه با منطق **Zero-Bypass** پیاده‌سازی شده است:

```text
       [Actor Request: API / UI / WebDAV]
                       │
                       ▼
    ┌─────────────────────────────────────┐
    │  احراز هویت کاربر (User Session)     │
    └──────────────────┬──────────────────┘
                       │
                       ▼
    ┌─────────────────────────────────────┐
    │ آیا کاربر در جدول oc_group_admin    │
    │ برای group_id مشخص‌شده ثبت است؟     │
    └──────────┬──────────────────────────┘
               │
       ┌───────┴───────┐
       ▼               ▼
     [خیر]           [بله]
       │               │
       ▼               ▼
┌──────────────┐ ┌─────────────────────────────────────┐
│ 403 Forbidden│ │ بررسی قلمرو هدف (Target Scope Check)│
│  سلب قطعی   │ │ آیا فایل/پوشه متعلق به همین گروه است؟│
└──────────────┘ └──────────────┬──────────────────────┘
                                │
                        ┌───────┴───────┐
                        ▼               ▼
                      [خیر]           [بله]
                        │               │
                        ▼               ▼
                 ┌──────────────┐ ┌────────────────────┐
                 │ 403 Forbidden│ │ انجام عملیات تگ    │
                 │ خطای امنیتی  │ │ ثبت در لاگ ممیزی   │
                 └──────────────┘ └────────────────────┘
```

## ۳. ساختار پایگاه داده و ذخیره‌سازی داده‌ها (Database & Storage Architecture)

### ۳.۱. جدول ممیزی حاکمیت تگ‌ها (`oc_archive_tag_audit`)
توسط مایگریشن نسخه `Version2100Date20260918000001.php` جدول اختصاصی ممیزی با ایندکس‌های بهینه‌سازی‌شده برای ممیزی عملیات در دیتابیس PostgreSQL ایجاد گردید:

```sql
CREATE TABLE oc_archive_tag_audit (
    id BIGSERIAL PRIMARY KEY,
    actor_uid VARCHAR(64) NOT NULL,
    group_id VARCHAR(64) NOT NULL,
    action VARCHAR(32) NOT NULL,
    tag_id INT DEFAULT 0,
    tag_name VARCHAR(255) DEFAULT '',
    target_type VARCHAR(32) DEFAULT NULL,
    target_id BIGINT DEFAULT NULL,
    target_path VARCHAR(1024) DEFAULT NULL,
    result VARCHAR(32) NOT NULL,
    details TEXT DEFAULT NULL,
    created_at BIGINT NOT NULL
);

CREATE INDEX idx_archive_tag_audit_actor ON oc_archive_tag_audit (actor_uid);
CREATE INDEX idx_archive_tag_audit_group ON oc_archive_tag_audit (group_id);
```

### ۳.۲. معماری نام‌گذاری تگ‌ها در هسته Nextcloud (`oc_systemtag`)
جدول هسته `oc_systemtag` دارای قید یکتایی `UNIQUE (name, visibility, editable)` است. جهت جلوگیری از تداخل نام تگ‌ها میان بخش‌های مختلف سازمانی و در عین حال حفظ نام تمیز و کاربرپسند در رابط کاربری:
- **نام ذخیره‌شده در سیستم:** `[<groupId>] <tagName>` (مانند `[SOC] فوری_پدافند`)
- **نام نمایشی تمیز در UI:** `فوری_پدافند` (از طریق تابع `extractCleanTagName`)
- **تفکیک و ایزولاسیون:** جدول واسط `oc_archive_tag_groups` تگ موردنظر را منحصراً به `groupId` منتسب می‌کند؛ در نتیجه کاربران سایر گروه‌ها به دلیل شرط `archive_tag_groups` این تگ را در پورتال یا API هرگز دریافت نمی‌کنند.

## ۵. تعبیه در رابط کاربری پورتال آرشیو (Portal UI Integration)

### ۵.۱. دکمه مدیریت تگ‌ها در نوار ابزار
در صورت داشتن نقش ادمین گروه (`is_group_admin === true`)، دکمه «🏷️ تگ‌های گروه» به نوار ابزار اصلی پورتال اضافه شده و با کلیک روی آن، مدال جامع مدیریت تگ‌های گروه باز می‌شود.

### ۵.۲. مدال جامع مدیریت تگ‌های اختصاصی گروه
- **انتخاب گروه:** برای ادمین‌هایی که مدیریت بیش از یک گروه را بر عهده دارند.
- **فرم ساخت تگ:** امکان وارد کردن نام دلخواه و دکمه `+ ایجاد تگ` با فیدبک آنی.
- **جدول تگ‌های ثبت‌شده:** نمایش نام تمیز تگ، تعداد اسناد متصل، و دکمه قرمز `🗑️ حذف` همراه با تأییدیه قبل از اجرا.

### ۵.۳. کشوی جزئیات سند (Slide-out Quick View Drawer)
- برای اسناد متعلق به گروه تحت مدیریت، بخش جدیدی به نام **«🏷️ الصاق تگ اختصاصی گروه»** نمایش داده می‌شود که شامل انتخاب‌گر کشویی تگ‌های موجود گروه و دکمه `+ الصاق به سند` است.
- در کنار نشان‌های تگ‌های اختصاصی متصل به سند، دکمه ضربدر قرمز (`✕`) تعبیه شده که به ادمین همان گروه اجازه می‌دهد بدون باز کردن صفحات دیگر، تگ الصاقی را درجا از سند حذف نماید.

### ۵.۴. تفکیک قطعی تگ‌های خودکار سیستمی و منع حذف آن‌ها توسط ادمین گروه (System Tag Deletion Guard)
- **فیلترینگ دیداری در مدال مدیریت تگ‌ها:** تگ‌های تولیدشده خودکار توسط سیستم (مانند تگ پوشه گروه `CERT`, `SOC` با مالک `system` و تگ‌های ایجادشده توسط مدیر ارشد سامانه با مالک `admin`) به هیچ وجه در فهرست مدال «مدیریت تگ‌های اختصاصی گروه» نمایش داده نمی‌شوند. ادمین گروه منحصراً تگ‌های دستی تعریف‌شده توسط خود ادمین برای همان گروه (با پیشوند `[<groupId>] `) را مشاهده و پایش می‌کند.
- **گیت امنیتی بک‌اند در متد `deleteGroupTag`:** هرگونه تلاش مستقیم یا API ادمین گروه جهت حذف تگ‌های با مالک `system` یا `admin` یا تگ‌های فاقد پیشوند گروهی، در لایه بک‌اند با خطای قطعی `HTTP 403 Forbidden` مسدود گردیده و مانع از آسیب یا حذف تصادفی تگ‌های اصلی ساختار پوشه‌بندی و بایگانی سازمانی می‌شود.

سوئیت آزمون جامع در فایل `tests/test_group_admin_tag_governance.py` پیاده‌سازی شده و تمامی تست‌ها با نتیجه قبولی ۱۰۰٪ اجرا گردیدند:

| شماره | عنوان سناریوی آزمون | وضعیت | شرح نتیجه اعتبارسنجی |
| :---: | :--- | :---: | :--- |
| **۱** | آپلود سند و حفظ تگ‌های خودکار | **PASS** | آپلود سند در پوشه گروهی تگ‌های سلسله‌مراتبی پوشه والد را خودکار دریافت کرد. |
| **۲** | ایجاد تگ توسط ادمین گروه | **PASS** | کاربر `Bakbari` تگ اختصاصی گروه `SOC` را با موفقیت ایجاد کرد. |
| **۳** | الصاق تگ به فایل در قلمرو گروه | **PASS** | تگ گروهی به فایل منتسب شد و در لیست فایل‌ها منعکس گردید. |
| **۴** | منع ایجاد تگ توسط کاربران عادی | **PASS** | کاربران `archive_user1` و `Adli` با خطای قطعی `403 Forbidden` مسدود شدند. |

| **۷** | منع دور زدن توسط ادمین سیستم (Zero-Bypass) | **PASS** | کاربر `admin` بدون عضویت در نقش Subadmin گروه با `403 Forbidden` مسدود گردید. |
| **۸** | هم‌زیستی تگ‌های خودکار و دستی | **PASS** | تگ‌های خودکار پوشه و تگ‌های دستی گروهی بدون هیچ تداخلی روی سند فعال ماندند. |

| **۱۰** | فیلتر چندتگی و ایزولاسیون دیداری | **PASS** | تگ‌های اختصاصی `SOC` صرفاً برای اعضای `SOC` قابل مشاهده و فیلتر بود و از دید `CERT` پنهان ماند. |

## ۸. حاکمیت اتمیک حذف تگ، رفع موفقیت کاذب و موتور خودترمیمی (Atomic Deletion & Consistency Engine)
> [!NOTE]
> *این بخش بر اساس تجمیع سند نیازمندی ۲۰ (Atomic Group Tag Governance & Consistency) به این سند الحاق شده است.*

### ۸.۱. رفع آسیب‌پذیری موفقیت کاذب (Elimination of False-Success)
در معماری بازطراحی‌شده، متد `GroupTagService::deleteGroupTag` از ارسال پاسخ موفقیت کاذب (`status: success`) قبل از اطمینان کامل از اجرای موفق تمامی کوئری‌های پایگاه داده ممانعت به عمل می‌آورد:
1. **مرز یکپارچه تراکنش (Unified Transaction Boundary):** تمامی عملیات پاکسازی در جداول هسته (`oc_systemtag_object_mapping`، `oc_systemtag`، `oc_systemtag_group`) و جداول آرشیو (`oc_archive_tag_groups` و `oc_archive_tag_ownership`) درون یک تراکنش اتمیک در PostgreSQL اجرا شده و در صورت بروز کوچک‌ترین استثنا، کل عملیات Rollback می‌شود.
2. **قفل سطری بدبینانه (`SELECT ... FOR UPDATE`):** روی رکورد مالکیت تگ اعمال می‌شود تا از بروز Race Condition و حذف همزمان جلوگیری گردد.
3. **پیشگیری از حذف تگ‌های در حال استفاده (`409 Conflict`):** سیستم قبل از حذف، انتساب تگ به فایل‌ها را بررسی می‌کند؛ در صورت وجود اسناد متصل، خطای ۴۰۹ با کد `TAG_IN_USE` صادر شده و صرفاً با سوئیچ صریح `force: true` اجازه حذف داده می‌شود.
4. **موتور بازآشتی و خودترمیمی (`reconcileGroupTags`):** کشف و پیوند مجدد تگ‌های یتیم جامانده از گذشته و پاکسازی رکوردهای فانتوم بدون مالک با دستور:
   ```bash
   php occ archive:tag:gov reconcile-group <groupId>
   ```
